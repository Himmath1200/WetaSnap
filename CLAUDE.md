# WeTa Snap — notes for Claude

- The spec is URS v2.0 (Lean Phase 1) in `docs/`, plus the client's additions of 20 Sep 2026 (themes, notifications, tags, import/export, templates, subscriptions, audit log, support — see README "Beyond the URS"). Tag code with its requirement IDs (e.g. `// LEAD-05`). There are still exactly three roles: super_admin, client_admin, staff. Do not add roles, badge scanning or the AI lead brief.
- Two doors (`lib/portal.ts`): the WeTano Console under `/super-admin` with its own sign-in page, and one shared address for client admins and staff (`/signin`, then plain paths). Build links with `linkFor(role, path)`; `routes.ts` (`SCREENS`, `canSee`, `homeFor`) decides what each role may open, and an account at the wrong door is refused with guidance. Sign-in is password-first for everyone; admins then get an emailed code (`AuthStep` in `lib/backend/index.ts`). An authenticator is never required — it is asked for only by accounts that turned it on themselves in Security, so never add a rule that forces it. Staff may soft-delete their own leads (client decision overriding URS §4.3). Nobody signs themselves up: every company account is invited (WeTano creates the client, the client admin the team) and the invitation email carries a 6-digit code **and** a "Set up password" button to `/signin#setup=<email>`, where the person enters the code and chooses a password, then gets "Go to sign in".
- Two sides, one contract: `apps/web` (Preact PWA) and `services/api` (NestJS + TypeScript on PostgreSQL). `apps/web/src/lib/types.ts` is the shared domain contract — the SQL in `services/api/db/migrations` must match it field for field.
- Every server call goes through the `Backend` interface (`lib/backend/index.ts`). There are two implementations and they must follow the same rules (roles, seats, licence status, idempotent sync, AI never overwrites a person's value): `api.ts` (the real backend, used when `VITE_API_URL` is set) and `demo.ts` (an in-browser mock, so the app runs with nothing installed — this is also what the tests use).
- API rules: every request a signed-in person makes runs on the `wetasnap_app` pool inside a transaction that sets `app.person_id` / `app.company_id` / `app.role`, so the row-level policies in `0006_rls.sql` apply (`db.as(me, …)`). Only sign-in, background jobs and migrations use `db.query` / `db.tx`, which run as the owner and are not policed — each of those call sites carries its own check. Password hashes, codes, CRM secrets and the job queue have no grant for the app role at all. Validate every body with zod (`common/validation.ts`), and raise `DomainError` for anything a person should read.
- The scanning pipeline is one path, in this order: quality check → crop → OCR → AI extraction → validation → normalisation → duplicate check → merge or create contact → enrichment → lead score → follow-up (`modules/scan/pipeline*`, `modules/contacts`). Everything up to normalisation answers the request; the rest is a job. Do not add a second route that writes leads or contacts around it.
- Failures go to the audit log — in the app through `lib/errors.ts` (`reportError`, and every error toast automatically), on the server through `AuditService`. Don't swallow errors silently, and don't log personal data: `scrub()` masks it.
- Offline first: saves always go to IndexedDB first (`lib/sync.ts` → `saveLocal`); never delete unsynced data. The device owns the lead id, so syncing is idempotent.
- Size budget: no new runtime package in `apps/web` without checking `npm run size`. Load heavy things lazily (libphonenumber, tesseract, pages). The API has no such budget, but it has no ORM and no auth library on purpose — passwords, tokens, TOTP and web push are a few lines of `node:crypto` each.
- UI: use `t()` / `tn()` for every visible string (the English text is the key). One main green button (`btn-primary`) per screen; blue (`ocean-*`) for secondary actions and filters. Touch targets ≥ 44 px (`min-h-11`).
- Light and dark share one set of tokens: use `bg-surface`, `bg-subtle`, `text-ink`, `text-muted`, `border-line`, `card`, and the `brand-*` / `ocean-*` / status scales. Never hard-code `bg-white` or `text-slate-900` — the dark theme re-points the same variables, so no `dark:` variants are needed.
- Phones: inputs are 16 px below `sm` (smaller text makes iOS zoom on focus), sheets use `dvh`, and anything pinned to the bottom needs `env(safe-area-inset-bottom)`.
- Typography: the wordmark and titles use `.wordmark` / `.title` (Outfit); body text stays on the system font. Raised surfaces (menus, popovers) use `.pop`.
- The copyright line lives in `AppShell` — screens must not add their own `<Copyright />`.
- Security is policy-driven: `security_policy` decides password rules, lockout, idle timeout and device-session length, on both sides. Use `checkPassword()` / `passwordStrength()` from `lib/password.ts` wherever a password is chosen in the app, and `PasswordService` on the server; never invent separate rules.
- Bulk actions, sorting and the tick boxes come from `ui.tsx` (`Tick`, `SortHeader`, `SortMenu`, `BulkBar`) — reuse them rather than rolling new ones.
- Before finishing: `npm run typecheck && npm test && npm run build && npm run size` (both workspaces), and for anything that touches the API, run it against a real database.
